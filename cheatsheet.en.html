01

Where VibeIQ sits

Week 1
The sentence to be able to recite

VibeIQ sits upstream of PLM, in the creative-commercial gap where the product is still being decided rather than developed. It sits alongside PLM/ERP/PIM/DAM, not in their place, and integrates bidirectionally with them.

The GTM calendar is the backbone: trend → line planning → design → line review → development & sourcing → sell-in → production. VibeIQ lives in the top half; tech packs, BOM, costing and POs belong to PLM and ERP.

The system landscape

SystemOwnsExamples
PLMTech packs, BOM, costing, samplesCentric, FlexPLM, Backbone
ERPPOs, inventory, financeSAP, NetSuite, Oracle
PIMPublished commerce attributesAkeneo, Salsify, inRiver
DAMMaster assetsBynder, Aprimo, AEM
Merch planningOTB, store clusteringo9, Blue Yonder, Anaplan

What VibeIQ actually replaces: Miro, Excel, PowerPoint — not the systems above. Board ↔ Miro · Plan ↔ Excel · Showcase ↔ PowerPoint.

The three apps and the platform

  • Board — trend research, mood boards, creative direction.
  • Plan — line planning. « Each row represents an actual product record »: the grid is a view onto entities, not a document.
  • Showcase — line reviews; stays live, and feedback flows back into the product record.

Underneath: Product Data Platform · Agent layer · Event & workflow engine · Integration & app platform (connectors, APIs, MCP server).

Brands

Contrail = the technical sub-brand (developer docs). VibeIQ = the commercial brand. Same product.

03

The data model — the key module

Week 2

Almost every escalation resolves here: which entity holds the value, at which property level, under which federatedId?

The three layers

EntityScopeAnswers
ItemOrg-wide, season-independent« What is this product, in general? »
ProjectItemOne Project (≈ one season)« What is this product for SS26? »
AssortmentItemOne Assortment« Is it in this assortment, and on what terms? »

Strict, one-way nesting. Hence the Loader's pairing rules: PROJECT_ITEM « must be paired with ITEM »; ASSORTMENT must be paired with ITEM and may be paired with PROJECT_ITEM — the selection loads all three instances in the same load.

Property levels — Family, Option, All, Override

LevelBehaviourUse for
FamilyWritten on the Family and copied down to every OptionCategory, silhouette, description
OptionWritten on the Option onlyColour code, option image
AllManaged individually everywhere — no copy-downExplicit values with no inheritance
OverrideCopies down but can be overridden at Option levelPrice, margin target

CSV column suffixes to target the level: somePropertyFamily, somePropertyOption.

The three failures to recognise on sight

1 · Wrong level at design time. Price set to Family instead of Override → you cannot charge more for one colourway. The customer says « the system won't let us do it ».

2 · Copy-down clobber. Reloading a Family property overwrites manual entries at Option level. The customer says « our data was reset overnight ». The all-time classic.

3 · All vs Override. The team expects inheritance, gets none, and every option is empty. The customer says « the load didn't work ».

federatedId — the upsert key

« A value you provide which uniquely identifies the entity within an org. » If the entity does not exist → created; if it exists → updated. For Custom Entities only, absent a designated property, name is used.

The platform's #1 integration bug

Entities created in the apps by users have no federatedId. A customer runs a manual pilot, then wires up a Loader feed keyed on style number: everything loads as new, no errors, and they have two of everything.

The second-order question to ask on every account: where does the federatedId come from? If it derives from a mutable business value (a style number that gets renumbered), the upsert key changes and you harvest orphans. A stable, meaningless key beats a meaningful one.

Projects, Assortments, owners

A Project is the season container (nested folders, plans, assortments, showcases, boards). An Assortment can stand alone or have an owner — hence the load types ASSORTMENT, PLAN, BOARD, SHOWCASE. Board, Plan and Showcase are each backed by an assortment: three views onto the same kind of object, which is why a product moves from mood board to line plan without being recreated.

04

The publish lifecycle

Week 3
1Editing in a Plan
2Adopting images / colours / attributes
3A user triggers publish
4Plan rows are pushed into the Assortmentinternal commit
5An AssortmentPublishChange is created
The step everyone skips

Step 4. Publish is not « send to the PLM »: it is first an internal commit from the Plan to the Assortment. Downstream integration is merely a consumer of the record that commit produces. So a publish can succeed while the downstream sync fails — two separate investigations.

Anatomy of an AssortmentPublishChange

FieldContents
assortmentBaselineDownloadLinkS3 URL — the full state of the assortment at publish time
deleteDataDownloadLinkS3 URL — only the items removed in this publish
detailadds, updates, deletes, familyItemsRemoved

The baseline answers « what is true now »; the detail answers « what changed this time ». A serious consumer needs both: the detail for efficiency, the baseline for recovery.

The two rules that cause incidents

Deletes do not accumulate. Each change carries only the deletions from its own publish. Missing publish #15 means those deletions are missed permanently. The only remedy: re-baseline.

S3 links expire after 24 h. Re-fetching the change object regenerates the links. Store the change ID, never the URL.

05

The Loader

Week 4

A LoaderProcess is an asynchronous entity: status, configuration used, logs, metadata. Creating it queues the work. So a load is inspectable and comparable, not a command you fire and forget.

The two diagnostic fields

  • failureArea — read this first. Four values: NONE, PARSING_CSV, VALIDATING_DATA, TRANSFORMING_DATA. A single field narrows the fault to a quarter of the pipeline.
  • preprocessingStepResults — an array of file IDs, one per step. Each loader-process-step-<Step Name>.json file contains rows, errors, warnings. Diff two consecutive steps and the offending step is unambiguous.

The five phases

#PhasefailureArea
1CSV parsingPARSING_CSV
2ValidationVALIDATING_DATA
3PreprocessingTRANSFORMING_DATA
4Entity construction
5Upsert API by federatedId
Fail-fast — no partial loads

« If validation produces any errors, the load stops immediately with a VALIDATING_DATA failure area. » Errors stop, warnings let it continue, and « no partial loads occur ». Consequence: you fix and re-run, there is no reconciliation to do. Equally useful corollary: a « completed » load really did apply everything — if the data is wrong afterwards, the cause is transformation or configuration, not a half-finished job.

Error taxonomy

CONFIG · HEADER_MISMATCH · INVALID_DATA · VALIDATION_ERROR · DUPLICATE_FEDERATED_ID · SYSTEM_ERROR. Row-level issue: {rowNumber, columnIssues:[{columnName, message, issueType, data}]}. File/config level: {message, issueType}, with no row number.

The six preprocessing steps

#StepEffect
1Boolean conversionThe strings "true"/"false" become booleans
2federatedMappingsSource column → target property, or a literal applied to every row
3propertiesToRemoveDrops the listed columns
4Type transformations without warningsLabel→slug, label→value for option sets
5conditionalColumnsCreates/overwrites columns; {column} interpolation and JS expressions
6Type transformations with warningsReplays step 4 and reports this time
The gap between 4 and 6

Step 4 normalises silently so that step 5 works on clean values; step 6 replays and reports. So a value mangled in step 4 and then overwritten in step 5 never produces a single warning. Value inconsistent with the CSV and no warning anywhere → suspect the 4/5/6 interaction and read the artifacts instead of reasoning.

FieldRequiredRole

The four flags that change what a load is

1 · shouldSkipAssortmentPublish — the most dangerous

Set to true, the write goes straight to the database, bypassing the publish workflow: no change history, no summary recalculation, no composite assortment update, and no assortment|publish event. The load succeeds, VibeIQ is correct, the PLM is stale indefinitely, and nothing anywhere flags a problem. Legitimate use: high-volume backfill with no history needed. The real problem: it gets set « just for the migration » and stays in a reusable config forever. Check it before you blame the consumer.

2 · partialAssortmentUpdate — a default that deletes

Defaults to false = replacement. Full-load semantics: CSV items absent from the assortment → added; present on both sides → updated; identical → unchanged; « assortment items not in CSV → deleted ». Sending only the 40 changed styles does not update 40 items: only those 40 remain. The load reports success. Set to true, you get the boolean columns addField / dropField; an « add » on an existing item is treated as an update.

3 · assortmentSplit — the silent loss

Groups rows by fieldToSplitOn and maps each group to an assortment. « Rows with values not matching any entry are skipped » — skipped, not errored. One new category value, one typo, one trailing space, and those rows never load while the job reports success.

4 · workspaceIdentifier — and a genuine UI gap

Required as soon as loadType contains PROJECT_ITEM, « even when also loading assortments ». Vocabulary: a « project » in the UI is a workspace with workspaceType: 'PROJECT' in the API. The trap: the identifier « is not editable in the Hub UI; it must be set via direct PUT request » — an admin cannot fix it by clicking.

Family / Option in a CSV

Each row typically represents one option. Rows sharing an itemFamilyFederatedId become the options of one family, and the loader creates the parent family automatically. A row with an itemOptionFederatedId is an option; without one, it is a family on its own. name = family name, optionName = option name, typePath mandatory on every row (often via conditionalColumn), optionGroup = the axis (e.g. color).

style,styleName,colorName          → "federatedMappings": {
SH-4471,Tech Fleece Hoodie,Black       "itemFamilyFederatedId": "style",
SH-4471,Tech Fleece Hoodie,Navy        "itemOptionFederatedId": "colorName",
SH-4471,Tech Fleece Hoodie,Gold        "name":                  "styleName",
SH-9902,Trail Short,Black              "optionName":            "colorName"
                                     }
3 rows → 1 family (SH-4471) with 3 options, + 1 family (SH-9902) with 1 option.
The five-minute exercise

You can read a customer's property-level model straight off their CSV: columns that repeat within a family are Family properties; those that vary are Option; the one that is usually the same but occasionally differs for a colourway is Override. Five minutes that predict years of tickets.

federatedId mechanics, Loader side

  • « There is no configuration to say 'this column is my Federated ID'. » Sole exception: Custom Entity (defaults to name). Everywhere else the value must arrive under the right property name — via federatedMappings or a conditionalColumn.
  • « It is critical to ensure that federatedId values do not change between loads. »
  • Unrecognised CSV columns are silently ignored.
  • Validation catches duplicates within a file; nothing catches drift between two files.
  • A computed ID ("{familyNumber}.split('-')[0]") inherits the source field's formatting as a hidden dependency: ABC-123 → ABC_123 and the upsert key changes for every row.

CLI vs API, and the drift effect

CLIAPI / SDK
Commandcontrail load upload-and-load <File> <Config>Upload, then create the LoaderProcess
fileLocationAutomaticYou supply it
Stored configsUnavailable — loaderConfigurationId not supportedSupported
Good forLocal files, testing, one-offsProduction, automation

Because the CLI cannot use a stored config, it passes a local copy that drifts. Classic symptom: « the same file loads differently depending on who runs it ». Compare the config saved on each LoaderProcess before anything else.

What a load does to your workflows

Phase 5 performs upserts, so a load emits ordinary events: item|create for new rows, item|update for existing ones, same for project-item and assortment-item. A 20,000-row load = 20,000 trigger evaluations. Except that shouldSkipAssortmentPublish suppresses assortment|publish: entity workflows fire, the outbound integration stays silent.

Integrations — the data going out

Week 5
CriterionChange History PollingPublish Events
TriggerScheduled (time)Event (on publish)
LatencyMinutes to hoursNear real time
ComplexitySimpleRequires a webhook endpoint

That « scope » row decides most architectures. Events carry publishes only; an item change that never publishes is never carried. Many customers do both: events for latency, polling as a safety net.

Authentication

Base https://api.vibeiq.com/prod/api, headers X-Api-Key and X-Api-Org. Keys via contrail app getApiKey, format app:uEL7GCBZ7Xhd4w2z. Errors: 401 (key, expiry, wrong org slug) · 404 (missing or access denied or wrong entity type — it is not proof of absence) · 429 (backoff, batch).

Never promise a throughput

The platform is « rate-limited to ensure system stability » but the numbers are not published — higher limits go through support. (The « 15 req/hour » you find online belongs to vibe.co, a different company.)

The event path

{ "assortmentId": "25uDvGNpYhZHw2nt", "assortmentPublishChangeId": "lTuARQLrhgWHNr3k" }

The payload is thin, and the delivery mechanism is an Event Workflow: so « the event never arrived » is a week-7 investigation (Process List, paths, access grants, taskOutputs). Retrieval: GET /assortments/{assortmentId}/history/{changeId}.

Baseline structure: baselineData.assortmentItems[] → .item, .item.itemFamily, .projectItem. The week-2 layers are literally in the payload: mapping is a data-model decision, not plumbing.

Polling and its seam

/api/change-history with createdOn BETWEEN a AND b. A time filter is not a cursor — three failure causes:

  • Boundary exclusivity — inclusive: double processing; exclusive: records on the same instant are lost.
  • In-flight writes — committed after the query ran but timestamped before the boundary: lost.
  • Clock drift — a locally computed now skips windows.

Four guardrails: overlap the window (lastSync − margin) · idempotent processing · advance the timestamp from the max createdOn returned, not the local clock · never advance on partial failure. Symptom: a few missing records, no errors, not reproducible → go read the window calculation, not the data.

A resilient consumer — six risks

RiskResponse
S3 links expiring at 24 hPersist the change ID, re-fetch
Non-cumulative deletesTrack processed change IDs; on a gap, re-baseline
DowntimeReconcile against the baseline on restart
429Exponential backoff with jitter, batch, cache
Duplicate deliveryIdempotent writes keyed on entity + change
Partial failureTransactional application or a resumable journal

The habit to recommend: periodic reconciliation against a fresh baseline, which reports discrepancies instead of silently fixing them.

Webhook security — two directions

Inbound (external → VibeIQ)Outbound (VibeIQ → external)
EndpointPOST /api/trigger-webhooks/{ID}The customer's URL
VerificationX-Verify-Signature, optional, shared secretAPI key, HMAC, or IP allowlist
SetupCLI/API; the ID in the URL is a bearer credential« Configuration requires contacting VibeIQ support »

Recommend HMAC outbound; claim nothing about the robustness of inbound. Outbound setup goes through support → that is a lead time to put in the project plan.

The artifact that prevents arguments

An attribute ownership map: for each attribute, the authoritative system, the direction, the VibeIQ entity layer, the property level, and the conflict rule. « The PLM overwrote our margin target » is not a bug, it is the absence of that document.

07

Event Workflows

Week 6

« The main engine for reacting to system events and running apps. » Made of triggers, conditionals, actions, declared in app.yml under workflows:. Properties: identifier, name, triggerKey, isActive, public, parallelWorkerCount (1–30, default 5), messageGroupId, messageGroup + dynamicMessageGroupId, crons.

Six trigger categories

CategoryForm
System events{entityType}|{action} — item, project-item, assortment-item, plan-placeholder, custom-entity, comment, content
ManualtriggerKey: manual
Custom app event'@{publisherOrgSlug}/{appName}:{EventName}'
Declared trigger keyexternal-event entity with details.eventType
Scheduledcrons
WebhooktriggerKey: "webhookId:WEBHOOK_ID"
The trigger that does not exist

assortment has only assortment|publish. There is no assortment|update. Any requirement that assumes one has to be redesigned — and it is a frequent cause of « the workflow never fired ».

Paths and conditionals

workflowDefinition.paths is ordered: « only the first path whose conditional evaluates to true is executed; the remaining paths are skipped ». These are if/else-if, not independent rules — one over-broad conditional at the top of the list turns everything after it into dead code, silently.

  • {newData.<slug>} — the state after
  • {oldData.<slug>} — the state before, absent on creates
  • {propertyDiffs.<slug>.<oldValue|newValue>}
  • {changeObjects} — for bulk-change workflows
Create vs update

{newData.x} !== {oldData.x} does not behave the same on create and on update. A bulk load creates thousands of entities at once: the workflow notifies for part of the file and not for the rest. It looks like a bug; it is not.

Actions, grants, execution

An action references a key from the app's actions, with an optional config « merged with runtime context » — hence the promotion risk: a staging endpoint in a production workflow's config. accessGrants bound what actions can touch: read (get, query) / write (get, query, create, update, delete). A workflow that runs and does nothing is often a missing grant.

One task at a time, in order

Each firing creates a process, which contains tasks. « Only one task runs at a time in a process, and tasks always run in order. If one task fails, none of the subsequent tasks are run. » Later actions are never executed, not « failed ». Put the riskiest action last, and never infer that a late action ran just because the process exists.

Concurrency and message grouping

  • Static: messageGroupId: X + parallelWorkerCount: 1 → strictly one at a time.
  • Dynamic: messageGroup + dynamicMessageGroupId: 'X-{newData.itemFamilyId}' → same key serialised, different keys in parallel.
  • Defaults: 25 concurrent processes per workflow, 60 per organisation, adjustable through the CSM.

Two field lessons: the org ceiling is shared, so one chatty workflow starves the others (« our other integration got slow on Tuesday »); and raising parallelWorkerCount without grouping turns a performance complaint into data corruption.

Lifecycle and observability

app.yml → contrail app publish → Workflow Template Definitions → contrail workflow-template-definitions install in the org. So changing a workflow is a release, not a setting.

Admin Console → Process List, reverse-chronological. UI/API statuses: Pending/PENDING, Processing/ACTIVE, Awaiting/AWAITING, Completed/COMPLETE, Failed/FAILED. Programmatic fields: status, taskOutputs, triggerEvent, startTime, endTime.

The evidence has a shelf life

« After 90 days, workflow logs (including the list of processes and tasks) are permanently deleted. » And above all: « once deleted, the process list, task list, and logs for a workflow is lost » — deleting a workflow destroys the audit trail immediately. Deactivate, do not delete.

The « why didn't it fire? » ladder

  1. Is there a process? (none → the trigger never matched; yes → jump to 5)
  2. isActive, installed in this org, from the expected app version?
  3. The right triggerKey? (classic: expecting assortment|update)
  4. Did the change emit that event? (a bulk load emits create)
  5. Which path ran? Read triggerEvent, evaluate top to bottom.
  6. Did the actions succeed? taskOutputs. COMPLETE but with no effect = access grant or wrong config.
  7. Intermittent and load-correlated? → concurrency, not logic.

Configuration, apps, extensions

Week 7

A spectrum, not a binary. Cost, time-to-change and skill requirements rise together.

LevelWhatWho / how
L0Types & propertiesAdmin
L1Formulas, rule sets, validation functions, blueprintsConfig, no deployment
L2Workflows & actionsCode, inside an app
L3ExtensionsCode + hosted UI
L4External systemsOff-platform

Default question: what is the lowest rung that genuinely solves the problem? Not the lowest rung in absolute terms — an L1 answer to an L2 problem is a fragile stack of formulas.

Formulas — three silent failures

  1. Misspelled slug → undefined, no error. Check every slug against the real Type before saving.
  2. « Updates to Reference Data does not cause Formulas to re-run » → right at write time, stale forever after.
  3. « On the Frontend, only Formulas in Plans are run »; a single level of object hydration.

Timing: create + update; ProjectItem formulas replay on Item update; a Plan publish triggers every Item, ProjectItem and AssortmentItem formula.

Rule Sets

They control editable, required, optionSetValues, minValue/maxValue, validationFunction per slug according to entity state. Semantics: outer array = OR, inner criteria = AND, « editability is locked wins », and validation constraints accumulate.

To confirm internally

They « evaluate client-side, affecting editor experience for all users ». Working assumption: a UX guardrail, not an integrity guarantee — Loader/API writes probably bypass them. That changes how you design validation for any integrated field.

Configuration Copy — environment promotion

contrail types getAll (export) / contrail types loadAll (import). Eleven categories, a YAML tree. Types keyed on typePath (item:footwear), hierarchies and policies on identifier. Three consequences:

  • Config is text → put it under version control. The cheapest maturity gain available.
  • Whole-org export, no cherry-picking → promotion is wholesale, and environments drift without discipline.
  • Config and apps are promoted by two different mechanisms (types loadAll vs app publish/install). A promotion is two things that have to stay in step.

Apps — three settled facts

The commercial landmine

The app identifier is globally reserved and immutable after creation (org@domain/app-name). And: « the org that first creates an app is the owner… App ownership can not be modified. » If an integrator creates the app in their org, the customer can never own it; the only remedy is a rebuild under a new identifier. Ask the question before anyone runs app create.

Visibility in app.yml: private (default) · private + accessGrants[{orgSlug, permissions:[install]}] · public. A public marketplace listing requires VibeIQ validation through the CSM.

Extensions

Manifest: identifier, name, userApps: [BOARDS, PLAN], display, iframeUrl, extensionType. Three types: DOCUMENT_AUTOMATION, CONTEXTUAL_ACTION, ADMIN_UTILITY. Display modal (centred dialog, focused tasks) or side-menu (right-hand panel, inspection tools).

What it commits you to

An extension requires public HTTPS hosting: that is a service the customer operates — availability, TLS, deployments, on-call. When it goes down, users report a VibeIQ outage. Settle hosting ownership and monitoring before go-live.

Week 8
The org is the boundary

Isolation, ownership, configuration and capacity are all bounded by the org. An environment is just another org — there is no environment abstraction above it. So dev/staging/prod is a convention held up by discipline, and promotion (two mechanisms, no reconciliation) drifts silently.

« VibeIQ has no user permission model » is false: Type Policies exist and are among the 11 Configuration Copy categories. What is missing is the documentation, not the capability. Still unknown: how those policies map onto named roles in the apps.

Credentials

  • app:… keys, long-lived. Never in the repo; environment variables or a secrets manager; one key per environment; rotation and revocation.
  • The CLI caches auth in ~/.vibeiq/configs/ — a credential store on every laptop that has run it. Offboarding must include a revocation.
  • A webhook's trigger URL contains the ID = a bearer credential.

Runtime

nodeRuntime: "nodejs22.x" in app.yml. Every customer with a custom app carries a maintenance obligation nobody budgeted for: track which accounts have apps and on which runtime.

The unknowns we own up to

  1. User roles and Type Policy mapping

« I don't know, I'll come back to you Thursday » — specific and honoured — beats a bluff. Bluffing a compliance answer is unrecoverable.

The diagnostic method

Weeks 9–10
The rule

The first question is not « why is this happening? » but « which segment of the pipeline am I in? ». Locating is cheap — the platform records almost everything — and it eliminates whole categories in one check.

Six checkpoints — and where to start

CPSegmentWhat you look at
1SourceIs the value correct in the original file?
2LoaderLoaderProcess: status, config used, per-step artifacts (diff)
3EntitiesWhich layer, which property level, which federatedId?
4Workflows / formulasProcess List: fired? which path? taskOutputs?
5PublishIs there an AssortmentPublishChange? Did the rows reach the assortment?
6ConsumerReceived? Processed — including the deletes?

Bisect: start at CP3. Correct there → the problem is downstream. Wrong there → it is upstream. One look halves the search space.

Symptom shape → cause class

What the customer describesLook for
Intermittent, load-correlated, never the same recordsConcurrency race
Constant, silent, every recordConfiguration
Only part of a batchCreate vs update divergence
« It started on the 12th, we changed nothing »Deployment, config promotion, or an expiry
A few missing, not reproducibleIntegration seam (polling window)
Right on write, wrong laterRecalculation or copy-down
Only some usersPermissions or client-side rules
Everything is slowShared capacity (org ceiling)
The highest-yield question

« If you re-run it, is it the same record that fails? » The same one → logic or configuration. A different one → timing or concurrency.

What a good escalation contains

  1. The segment, located — not « X is broken »
  2. The identifiers (process IDs, change IDs, org)
  3. What you ruled out, and how — most often omitted, and the one that saves the most time
  4. The shape of the symptom
  5. Business impact and deadline
  6. Your hypothesis, labelled as a hypothesis

With the customer: explicitly separate known / suspected / unknown, commit to a time for the next update rather than a time for resolution, give them something to do, and close with the mechanism, not just « it's fixed ». Never answer « whose fault is it? » — answer « here is what happened and what we are changing ».

Self-assessment

Twelve questions in the shape the exam takes. Say the answer out loud, then unfold. A « roughly right » answer counts as wrong: it is the exact terms (failureArea, « no partial loads occur », assortment|publish) that are marked.

What are the three entity layers, and what question does each answer?

Item — org scope, season-independent: « what is this product, in general? ». ProjectItem — one project ≈ one season: « what is this product for SS26? ». AssortmentItem — one assortment: « is it in, and on what terms? ». Strict nesting, hence the Loader pairing: PROJECT_ITEM must be paired with ITEM, ASSORTMENT with ITEM and optionally PROJECT_ITEM.

Difference between the All and Override property levels?

Override copies the value down to every option but allows a different value on a specific option — it is the level for price or a margin target. All manages the value individually on each entity in the family and « no copy down behavior exists » — no inheritance at all. Confusing the two produces the « all our options are empty » symptom.

A customer has two copies of every product. Most likely hypothesis, and the question to ask?

The entities were created by hand in the apps: they have no federatedId. The Loader feed wired up afterwards has nothing to match on and creates everything fresh, with no error. Question: « were these records created in the UI before the first integration, and were they assigned a federatedId via the API? » Variant: the federatedId is computed and its source changed format.

What exactly does step 4 of the publish lifecycle do, and why does it matter?

It persists the Plan rows into the underlying Assortment — an internal commit. Publish is not « send to the PLM »: the AssortmentPublishChange created next is merely a record an external consumer comes to fetch. So a publish can succeed while the downstream sync fails, and those are two different investigations.

A consumer missed publish #15. What did it lose, and how do you repair it?

The deletions from that publish, permanently: « delete data does NOT accumulate across publishes », each change carries only its own deletes. Adds and updates will be caught up by a later baseline; deletes will not. The only remedy: re-baseline against assortmentBaselineDownloadLink and reconcile. And if the consumer stored the URL instead of the change ID, it cannot even re-download it — the links expire in 24 h.

A load reports « completed » and the PLM received nothing. What do you check first?

shouldSkipAssortmentPublish in the configuration saved on the LoaderProcess. Set to true, the write bypasses the publish workflow: no change history, no summary recalculation, no composites, no assortment|publish event. The load genuinely succeeded, VibeIQ is correct, and nothing signals that downstream is stale. Check the flag before blaming the consumer.

The customer sends only the 120 changed styles. What happens, and which field changes the answer?

The assortment is reduced to those 120 styles: partialAssortmentUpdate defaults to false, and full-load semantics say « assortment items not in CSV → deleted ». The load reports success. The field that changes everything is partialAssortmentUpdate: true, with the boolean columns addField / dropField (an « add » on an existing item is treated as an update).

Why do type transformations run twice, and what can be lost between the two?

Step 4 normalises silently so that step 5's conditionalColumns work on already-clean values; step 6 replays the transformation and this time reports the warnings. What gets lost: a value mangled in 4 and then overwritten in 5 never generates a warning. Symptom: the value does not match the CSV, and there is no warning anywhere.

A workflow must react to any assortment change. What do you answer?

That the trigger does not exist: assortment has only assortment|publish. The requirement has to be redesigned — react to entities (assortment-item|update) if the content is what matters, or accept publish granularity. It is also the classic cause of « our workflow never fired »: the third rung of the diagnostic ladder.

A process is COMPLETE but nothing was written. The two causes?

A missing accessGrant (the action is not allowed to write that entity type) or a wrong config (the action did run, but pointed elsewhere — a staging endpoint promoted into production, for instance). Useful reminder along the way: within a process only one task runs at a time, in order, and if one fails the following ones are never executed — not « failed ».

A customer raises parallelWorkerCount from 5 to 20 to go faster. What happens?

Without message grouping, you convert a performance complaint into data corruption: events touching the same family are now processed in parallel and step on each other. And because the 60-processes-per-org ceiling is shared, this workflow starves the others — « our other integration got slow ». The right answer is messageGroup + dynamicMessageGroupId to serialise by key.

Symptom: a few records go missing now and then, no errors, not reproducible. Where do you go?

Into the polling window calculation, not the data. A time filter is not a cursor: boundary exclusivity, writes committed after the query ran but timestamped before the boundary, clock drift. The four guardrails: overlap the window, idempotent processing, advance the timestamp from the max createdOn returned, and never advance on partial failure.
